# Page-specific capture readiness after the fifth production run

Root's fifth full production E2E at `8426f13` recorded 238 passed, one failed, ten existing skips and twenty not run. P3C's six-state flow passed. P3D stopped on its first `read-only-r1` capture: the PNG was 2944 px high and the immediately following page measurement was 2969. The shared synchronous layout sampler prevents detached-node measurements; it does not establish completion of independent React readers.

## Actual component counterexample

`ValidationDetailPage` mounts `AppendRevisionPanel` immediately. Its current draft and Product reads are independent; the visible current-base heading proves only the former. After the parent validation read completes, it separately mounts `ApplyDraftPanel`, whose own current-draft/Product reads and local-anchor timer are independent again. P3D's `openSource()` waited only the append heading. The first-application panel can still show its loading paragraph, then add the existing-draft fact.

`tests/browser/studio-drafts-capture.ts --revision-probe` mounts those actual components with controlled synthetic HTTP and extracts the old screenshot function unchanged from `8426f13`. It holds only Apply's draft read until the old PNG has actually returned, then releases that read before the old helper's existing post-capture height measurement. Evidence `.cache/p4-drafts-capture/1792486576449/result.json` reproduces **2944 → PNG 2944 → page 2969**. Only the first-application panel changes height (464.140625 → 489.734375); append/recovery panels are unchanged, fonts are loaded and there are zero animations. The original full-height assertion fails. The retained root PNG in `.cache/p4-e2e-fifth-failure/test-results/studio-draft-revisions-rea-f6e56-d-executes-fixed-r1-scoring-studio-draft-revisions/` was also inspected at native size: it visibly contains Apply’s initial-read paragraph and disabled refresh control while Append already shows revision 1, corroborating this controlled boundary. No computed height or success result is fabricated. Earlier probe attempts remain separate cache directories.

Entry/report HTTP or a ready export button does not establish this screen task's readiness. Fonts are awaited at each width. Existing raw-token DOM and 44 px target checks remain unchanged.

Operator key-list relies on its existing joint controller refresh/combobox readiness.

`consumer-host.ts --capture-readiness-only` exercises the actual host with held screen-resource HTTP. Evidence `.cache/p4-consumer-host/1792486830483/result.json` records four cover captures only after the real verified resource completes, four UNKNOWN-resume captures with the same anchor and no additional POST, and twelve result/report/poster captures. Its existing two expiry snapshots also execute (22 PNGs total, zero page errors). This does not replace the root's eight-case production consumer suite or the pending original-image review.
