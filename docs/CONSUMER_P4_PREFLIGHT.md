# P4 消费者闭环前置方案（未冻结）

2026-10-18。目标仍为历史人物首款内部端到端体验。P3-E 服务/后台及集成出口正在进行；本文只记录主控与独立架构审查的下一阶段准备，不是 P4 启动验收、已实现数据库表或公开发布批准。

## 执行版本方向

采用独立 `internal_play_version` 层，固定既有 `product_version` 的 ID/完整 snapshot SHA、Product、不可变源修订与三 hash、review 引用，以及真正消费者 renderer/engine 身份、logicHash、组件/字体和暂存/完成/报告协议。具体机器 Schema、上限与迁移须在 P3-E 出口后进一步冻结。

P3-E 版本保存的 `studio-internal-preview` 是来源历史，不能冒充消费者执行能力或作为 fallback。新的 play 层使用新协议与指纹域，不能修改旧 snapshot。源正文继续从已验证、不可变的原修订读取；报告完成时才保存完整不可变用户快照，不用另复制一份可变题库。

选择独立层的理由：旧版本 metadata/list 同样严格限定内部预览，且其完整列表和数据库全部 100 槽位共同支持永久 `capacity-exhausted` 证明。把新能力直接塞进同一表，会迫使旧解析器拒绝新行或静默漏行，进一步影响旧容量判断。独立层保留 P3-E 原 key、head-only、target-used、100 全行计数、不可删除及显式清锚语义。

新 play 创建默认仍限当前 head，原成功 key 优先；如果未来允许历史 head 新建，必须另立协议，不能静默改写原永久证明。新的引用写入继续沿 outer guard 与同事务非等待 shared 锁直至 COMMIT；维护清理须在首次 unlink 前检查 play/Key/session/report 留存，不能仅依赖数据库 FK 最后拒绝。

## 最小用户闭环

1. 运营员从已批准的首款精确版本准备内部答题版本，再发放固定该 playVersionId/snapshot SHA 的测试 Key；不改变公共发布指针。
2. 匿名访问者交换 Key 为独立消费者授权，进入同一会话；不需要注册，也不获得运营权限。
3. 选择答案与进度由服务器暂存，使用 revision 比较更新；刷新、重新打开原链接或更换设备恢复同一会话。冲突先展示服务器事实，不自动覆盖另一设备。
4. 完成请求绑定预期 revision 和规范答案 hash；服务端再次验证并执行固定确定性引擎，同一事务唯一写报告、锁定会话并消费 Key。未确认的完成保留原请求，核实后才允许后续操作。
5. 完成后原链接只读查看同一报告及 PNG，不能重新答题、重评分或再次调用模型。报告和海报不包含原始 Key 或可恢复会话的访问链接。

首版使用 DETERMINISTIC；不顺带实现 AI、支付、平台交易、公开分享授权或外部部署。人物、题目、评分规则、四报告和八图沿已批准内测基线；中性操作提示和真实保存/完成状态属常规工程。新消费者页面必须准确替换旧临时预览的“刷新重置”等状态说明，并由新的受控实现身份覆盖，不能原地改掉已封存的旧 renderer。

## 冻结前仍需明确

- Key 发放的原文一次交付、未知响应恢复和撤销方案；服务器仅保存摘要，日志/截图/公共仓库不含真实凭证。
- 匿名 grant 的 Cookie、CSRF、期限、撤销及完成后只读权限；本地 HTTP 与未来生产 HTTPS 的配置边界。
- Key/session/report 的精确外键、状态与唯一完成约束，暂存 CAS 和重复/并发完成的事务协议；不得把客户端状态或 HTTP 超时当提交权威。
- 新 play 创建、Key 发放与完成各自的有限请求、不可变 receipt、UNKNOWN 核实和永久未应用证明；采用最小必要协议，不复用含义不同的旧 key 域。
- 消费者 DTO 只提供获授权的题目/选项/进度，禁止评分权重和候选报告提前下发；最终 report DTO 来自锁定快照。
- 精确 renderer、静态字体、私有图片和报告读取的有界 IO/资源收口，历史版本与资源不可变留存。
- 先真实 PostgreSQL 并发、越权、断连和升级验证，再生产 Next 浏览器完整闭环、320/375/390/430 图检与实际 PNG；全部通过后才进入 P5 首款现场验收。
